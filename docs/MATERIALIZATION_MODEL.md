# Materialization Model

## 1. What is materialized

Materialization applies only to managed/derived views, not to all documentation.

```text
structured RawObject / transient DerivedObject
        ↓ renderer
managed output file
```

Plain Markdown remains outside this pipeline unless explicitly modeled as a semantic target.

## 2. Output ownership

For structured managed and fully-derived file outputs, `$docengine.materialize[]` in the mirrored JSON descriptor owns the output path. Builder/dependency logic remains in project code.

This separation means:

```text
docs/_structured/foo/bar.json   → identity + canonical data/descriptor + output ownership
docengine_project/builders/foo/bar.py → computation/dependency reads
docs/foo/bar.md                 → generated presentation
```

## 3. Normal regeneration policy

Preferred normal workflow:

```text
edit canonical structured data / project code
→ docengine sync
→ dependency check
→ selectively rebuild missing/build_required deterministic targets
→ materialize affected views
→ report semantic attention without auto-fix
```

`sync --all` broadens materialization selection to all registered outputs but does not force deterministic builders that remain valid to rebuild.

For inspection before any deterministic rebuild, run `docengine check` explicitly.

Release/reproducibility workflows may run full materialization followed by `verify`.

## 4. Renderers are presentation-only

Renderer input is already-built object/view-model data. Business/derived computation belongs in builders/pure helpers.

Current v0.1 built-in/runtime boundary:

```text
object
├→ built-in Markdown renderer → managed file
└→ project-defined renderer   → managed text/bytes file
```

Conceptually an application may add JSON/HTML/UI/API adapters, but gendocen v0.1 does not provide a built-in live application/query backend. An application adapter is an integration boundary, not proof of a persisted DerivedObject payload store.

## 5. Generated output is not canonical

If Markdown is a generated/materialized view, direct edits are transient drift. Before editing a visible `.md`, use resource inventory/descriptor metadata to identify ownership and edit the actual canonical source or builder.

`verify`/materialization drift checks should detect generated bytes that no longer match reproducible output.

## 6. Orphans

When a previously owned generated path is removed/renamed, the engine preserves the file and historical ownership state rather than deleting user-visible content automatically. Intentional ownership transition is explicit via the orphan-acknowledgement workflow.
